## Context

The previous database-analysis task has already produced the database design artifacts and SQL migrations, including the repository ERD and migration plan.

This task is the **execution-layer follow-up**.

Do **not** redesign the ERD or regenerate the database model unless an implementation blocker proves that an existing migration cannot be executed safely.

The goal is to make the Go backend own a clear, repeatable database lifecycle for:

```text
migration execution
migration inspection
migration validation
migration creation
rollback
bootstrap/reference seeding
development/demo seeding
seed inspection
```

The implementation must expose explicit developer/operations commands instead of requiring engineers to manually execute `.sql` files.

---

## Objective

Build migration execution under the Go project and establish a production-safe seeder blueprint.

The completed implementation must provide:

1. a Go-owned migration runner that consumes the existing migration `.sql` files;
2. explicit CLI commands for migration lifecycle operations;
3. a seeder framework with deterministic execution and tracking;
4. separation between required/reference seeds and development/demo seeds;
5. first-class Makefile execution support for the complete migration and seeder command surface;
6. configuration and environment-safety rules;
7. tests for migration/seeder orchestration where practical;
8. documentation containing the complete command surface and recommended workflows.

# 3. Migration Runner Requirements

The Go migration runner must consume the migration SQL generated by the previous task.

It must support, directly or through the selected migration library:

```text
validate migrations
inspect current migration state
apply pending migrations
rollback migrations
inspect current version
create a new migration skeleton
```

Migration execution must:

* use the same database configuration mechanism as the API where possible;
* fail fast when required database configuration is missing;
* return a non-zero exit code on failure;
* log migration version/name without logging credentials;
* preserve migration ordering;
* detect dirty/failed migration state if supported by the selected library;
* prevent concurrent migration execution when the selected tool/database supports locking;
* not edit previously applied migration files;
* use transactions when supported and appropriate;
* preserve the existing SQL dialect;
* make rollback behavior explicit.

### Migration source

Use the existing migration directory produced by the prior task.

Do not create a second competing migration directory unless the existing layout is unusable; if that occurs, record it as a plan variance.

# 4. Required Migration Command Surface

Expose equivalent commands even if the repository's preferred CLI syntax differs.

The final documentation must show the **actual implemented commands**.

Canonical capability contract:

```bash
# inspect / validate
db migrate validate
db migrate status
db migrate version

# execution
db migrate up
db migrate up --steps 1
db migrate down --steps 1

# create migration
db migrate create <migration_name>
```

If supported safely by the selected migration framework, also expose:

```bash
db migrate goto <version>
db migrate force <version>
```

`force` is a recovery command and must:

* be clearly marked dangerous;
* never run automatically;
* require an explicit command;
* be documented for dirty-version repair only.

### Command behavior

#### `migrate validate`

Validate migration discovery, naming/order, and parseability without mutating the database whenever possible.

#### `migrate status`

Display at minimum:

```text
migration version
migration name
applied / pending state
```

If the migration library cannot provide per-file status, implement the closest reliable representation and document the limitation.

#### `migrate version`

Display the currently applied version and dirty state when available.

#### `migrate up`

Apply all pending migrations by default.

Support `--steps N` when supported cleanly.

#### `migrate down`

Rollback only an explicit number of steps.

Do not make an unbounded full rollback the default.

#### `migrate create`

Create new migration file(s) following the repository's established naming/version convention.

Do not execute the new migration automatically.

# 6. Seed Categories

Seeds must be separated by purpose.

## A. Reference / bootstrap seeds

Examples include only repository-supported required data such as:

```text
lookup values
system statuses
required configuration types
stable master/reference rows
required application bootstrap values
```

Reference seeds may be valid in production **only when explicitly executed**.

They must be deterministic and idempotent.

Prefer stable natural keys/codes/UUIDs already established by the schema rather than relying on auto-increment IDs.

## B. Development / demo seeds

Examples:

```text
sample events
sample purchasers
sample participants
sample livestock
sample purchases
sample payments
sample operations data
```

Development/demo seeds:

* must never run implicitly in production;
* must be clearly separated from reference seeds;
* must be safe to recreate in local/test databases according to documented rules;
* must not contain real personal, payment, or production data.

Do not invent large demo datasets unless they are useful to current application development.

---

# 7. Seed Tracking

Implement seed execution tracking when the repository does not already have an equivalent mechanism.

Preferred concept:

```text
schema_seeds
-----------
name
checksum or version when justified
executed_at
```

Exact table naming must follow repository conventions.

The tracking mechanism must allow the runner to determine whether a deterministic seed has already executed.

Do not use migration-version state to represent seed execution.

Migration history and seed history are separate concerns.

If checksums are implemented, document how changed seed definitions are handled.

---

# 8. Seeder Idempotency Rules

Every reference seed must be safe against accidental duplicate execution.

Use repository-appropriate techniques such as:

```text
UPSERT
INSERT ... ON CONFLICT
MERGE
existence checks inside a transaction
stable unique-key based insertion
```

Choose syntax according to the verified SQL dialect.

Do not rely on generated numeric IDs as the only duplicate guard.

A seed that cannot safely be idempotent must explicitly declare that limitation in code/documentation and fail rather than silently duplicate data.

The exact syntax may follow existing CLI conventions, but all capabilities above must be represented or a limitation must be documented.

### Expected behavior

```text

```

#### `seed status`

Display:

```text
seed name
```

#### `seed run --group development`

Run local/demo seeds only and enforce environment safety.

# 12. Makefile Execution Surface — Required

Makefile support is a **hard acceptance requirement**, not optional convenience documentation. Every normal migration and seeder operation implemented by the Go database CLI must also be executable through repository Make targets.

The Makefile must remain a thin execution wrapper over the Go database CLI; migration/seeding behavior must not be reimplemented in shell recipes.

The Make targets must forward arguments to the Go command deterministically and return its exit code unchanged.

Required capability set:

```bash
make db-validate
make db-status
make db-version
make db-migrate
make db-migrate-steps steps=<n>
make db-rollback
make db-rollback-steps steps=<n>
make db-migration-create name=<name>
make db-seed-list
make db-seed-status
make db-seed name=<seed_name>
make db-seed-all
make db-seed-reference
make db-seed-development
make db-setup
```

Adjust naming to existing Makefile conventions rather than creating inconsistent targets, but preserve all capabilities above.

Also expose Make targets for any optional recovery/navigation commands that are actually implemented by the Go CLI, for example:

```bash
make db-migrate-goto version=<version>
make db-migrate-force version=<version>
```

`db-migrate-force` must remain explicitly dangerous and must never be included in `db-setup` or other automatic workflows.

### CLI ↔ Makefile parity

During PLAN, produce a mapping table similar to:

```text
Go CLI command                         Makefile target
---------------------------------------------------------------------
db migrate validate                    make db-validate
db migrate status                      make db-status
db migrate version                     make db-version
db migrate up                          make db-migrate
db migrate up --steps N                make db-migrate-steps steps=N
db migrate down --steps 1              make db-rollback
db migrate down --steps N              make db-rollback-steps steps=N
db migrate create NAME                 make db-migration-create name=NAME
db seed list                           make db-seed-list
db seed status                         make db-seed-status
db seed run NAME                       make db-seed name=NAME
db seed run --all                      make db-seed-all
db seed run --group reference          make db-seed-reference
db seed run --group development        make db-seed-development
db setup                               make db-setup
```

The table must be updated to the **actual implemented command names** in the final report.

### Makefile behavior requirements

Make targets must:

* execute the Go-owned DB command rather than raw migration SQL;
* forward `name`, `steps`, `version`, or equivalent variables with validation;
* fail with a clear usage message when a required Make variable is missing;
* preserve non-zero exit codes from the Go command;
* work from the documented repository root;
* avoid embedding credentials or environment-specific DSNs;
* reuse the application's established environment loading/configuration;
* avoid silently applying development seeds;
* avoid chaining rollback or force operations into normal setup targets.

Do not implement migration/seeding business logic directly in Makefile shell recipes.

# 19. Acceptance Criteria

The task is accepted when:

1. Engineers no longer need to manually execute migration SQL for normal workflows.
2. Existing migration SQL remains the schema source consumed by the migration runner.
3. Migration ordering and applied version are inspectable.
4. Pending migrations can be applied through an explicit Go-owned command.
5. Rollback requires an explicit bounded operation.
6. New migration skeletons can be created using a documented command.
7. Seeds are implemented through a registry/runner instead of ad-hoc startup code.
8. Reference and development seeds are clearly separated.
9. Reference seeds are deterministic and idempotent.
10. Development seeds cannot run accidentally in production.
11. Seed execution state can be inspected.
12. Every normal migration/seeder CLI capability is executable through a documented Makefile target with equivalent behavior.
13. Migration and seed failures return non-zero command exits.
14. Credentials and sensitive data are not logged.
15. API startup is not coupled to unsafe automatic migration/demo-seed execution.
16. Tests cover the core migration/seeder orchestration.
17. No migration is applied to staging or production as part of task execution.
18. No commit or push is performed.
